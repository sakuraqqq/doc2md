## 1. 新确认的 Bug（前四轮 + t23-t37 未覆盖）

### 1.1 xlsx 自解析按索引读 `sheetN.xml`，sheet 名与内容错位（P1，静默给错数据）

**位置**：`src/xlsx.js:258`（`xlsxSelfParse` 读表）与 `src/xlsx.js:307`（调用）；`xlsxSheetNames` 只解析 `xl/workbook.xml` 的 `<sheet name="…">` 顺序，**从未读 `xl/_rels/workbook.xml.rels` 的 `r:id → Target` 映射**。

```js
// src/xlsx.js:258 —— 按序号读文件
const entry = await zipEntry(buf, 'xl/worksheets/sheet' + (i + 1) + '.xml');
// 而 readNames[i] 来自 workbook.xml 的标签顺序（tab 顺序），两者不保证一一对应
```

**实测**（浏览器构造：workbook 顺序 First→`rId1`、Second→`rId2`；rels 映射 `rId1→worksheets/sheet2.xml`(BBB)、`rId2→worksheets/sheet1.xml`(AAA)）：

```
实际输出：### Sheet: First  → | AAA |      （应为 BBB）
         ### Sheet: Second → | BBB |      （应为 AAA）
```

无 error、无 warning——用户拿到张冠李戴的数据。

**真实触发**：Excel 中拖动工作表标签重排、复制/删除工作表后，OOXML 文件名与 workbook 顺序不再对应。删掉首个 sheet 时 `sheet1.xml` 不存在 → `zipEntry` 返回 null → 抛错 → 回退库路径侥幸正确；但**仅重排标签**时所有文件都存在 → **静默错位**。带 chartsheet（`xl/chartsheets/`）的 workbook 同样命中。

**修复方向**：
1. 新增 `xlsxWorkbookMap(buf)`：解析 `xl/workbook.xml`（name + `r:id`）与 `xl/_rels/workbook.xml.rels`（`Id → Target`），产出 `[{ name, target }]`；
2. `xlsxSelfParse` 按 `target`（前缀补 `xl/`）读文件，不再用 `sheet{i+1}`；
3. `xlsxSheetNames` 保留或改造为返回上述结构（注意向后兼容 H 组源码断言）；
4. 补契约用例：构造"workbook 顺序 ≠ 文件名顺序"的 xlsx（gen-samples 确定性生成），断言 `### Sheet: First` 后跟 BBB。

### 1.2 PDF 质量门槛误判 + 单页 OCR 失败导致整篇失败（P1/P2）

**位置**：`src/pdf.js:197-198`（门槛与未捕获的 OCR 调用）、`src/pdf.js:143`（`textQualityRatio`）

**实测**：构造文本层完全有效的 PDF（内容为 ASCII 符号 `~^&*+={}<>|/@#$…`，长度 >10），file:// 下转换结果：

```
转换失败：file:// 直接打开时 OCR 不可用（本地 worker/WASM 加载受限）——请改用本地 HTTP 服务……
……TXT/HTML/DOCX/XLSX/PDF 文本层等其余格式不受影响
```

错误文案自相矛盾：失败的恰恰是 PDF 文本层。README L36「其余格式（PDF 文本层/DOCX/XLSX/TXT·HTML）file:// 双击可用」因此并不成立。

**两层根因**：

1. `textQualityRatio` 的 GOOD 集 = CJK（4E00-9FFF）/假名（3040-30FF）/谚文（AC00-D7AF）+ ASCII 字母数字 + 少量标点；其余全部计入 garbage。于是**纯符号页、西里尔/希腊/阿拉伯/希伯来/泰文/印地文 PDF、全角字母数字、emoji 页**有效占比≈0 → 全部触发 OCR。俄语 PDF 会被 eng+chi_sim 模型 OCR，结果只会更差。
2. `await ocrPageToText(...)` 未包 try/catch；`getOcrWorker()` 在 file:// 下是**同步 throw**（`src/ocr.js`），离线首次 OCR 下载失败 / WASM 初始化失败同理。现有兜底只覆盖「OCR 返回空串」（`src/pdf.js:199-207`），覆盖不了「OCR 引擎起不来」→ **一页 OCR 失败即整篇转换失败**，哪怕该页有可用文本层。

**修复方向**：
- 质量判类改用 Unicode 属性（`\p{L}`/`\p{N}` 记有效），或只把私用区（E000-F8FF）/替换符（FFFD）/控制符记 garbage——CID 假文本层的特征本就是私用/未分配区密集；
- 每页 OCR 包 try/catch：失败时保留文本层原文 + warning（`第 N 页 OCR 不可用，已保留原文本层`），无文本才跳过；
- README/architecture 同步该限制。

### 1.3 xlsx 日期格式化回归（P2，README 宣称"日期/数字格式化"）

**位置**：`src/xlsx.js` `xlsxParseSheet` 默认分支 `return decodeXml(c.v)`——完全不读 `xl/styles.xml` 的 numFmt。

**实测对比**：

| 输入形态 | 自解析输出（当前主路径） | 库路径（原行为 / `architecture.md §4.4` 口径） |
|---|---|---|
| numFmt=14 日期 + 序列号 `45123`（Excel 最常见形态） | `45123` | `2023-07-16` |
| `t="d"` ISO 日期（`real-date.xlsx` 形态） | `2021-06-10T00:47:45.700Z` | `2021-06-10`（`Date → toISOString().slice(0,10)`） |

仓库 `real-date.xlsx` 恰好用 `t="d"`，因此现有断言 `includes('2021-06-10')` 对两种路径都绿——**序列号日期这一最常见形态无覆盖**。README L37 的「日期/数字格式化」与 `architecture.md §4.4`（仍写 read-excel-file 为主实现 + Date 格式化）均已过时。

**修复方向**：解析 styles.xml 的 numFmt（内置日期 id 14-22、27-36、45-47、50-58 + 自定义 formatCode 中的 y/m/d/h）→ 序列号转日期；或检测到日期样式即回退库路径；至少发 warning「日期已按序列号输出」并同步 README/architecture。

### 1.4 `decodeText` 的 FFFD 启发式过度触发：1 个坏字节毁掉整篇（P2）

**位置**：`src/sniff.js:67-72`

```js
if (headTxt.includes('\uFFFD')) {
  try { const g = new TextDecoder('gb18030').decode(buf); if (!g.includes('\uFFFD')) return g; }
```

GB18030 几乎能解码任意字节且无 U+FFFD，所以「出现任意 U+FFFD」≈「只要 GB18030 解码没 FFFD 就整篇改判 GB18030」。

**实测**：UTF-8 文本「你好世界，这是一个测试文档。」截掉最后一个字节：

```
实际：浣犲ソ涓栫晫锛岃繖鏄竴涓祴璇曟枃妗ｃ€      ← 全文按 GB18030 重解
应有：你好世界，这是一个测试文档�           ← 仅末字损坏
```

触发面：UTF-8 文件含 1 个坏字节（下载截断/磁盘损坏）或字面 U+FFFD 字符。t25 已登记为「低」，但后果是整篇报废，建议提级。

**修复方向**：加小比例阈值（如 FFFD 占比 ≥2% 才回退），或同时比较两种解码的 FFFD 数量与可读字符得分（UTF-8 仅 1 个 FFFD vs GB18030 全篇 CJK 时优先 UTF-8）。

### 1.5 `zipEntry` 越界仍抛裸 RangeError（P3，第四轮已报未修）

**位置**：`src/xlsx.js:35`（`dv.getUint16(localOff + 26, true)` 前无边界校验）

**实测**：构造 `PK\x03` 头 + 前 64KB 含 `xl/` + EOCD 指向越界 localOff 的损坏 xlsx：

```
转换失败：Offset is outside the bounds of the DataView
```

应为「回退库/单 sheet」而非把 DataView 异常透给用户。且 `xlsxConvert` 先调 `xlsxSheetNames`（`src/xlsx.js:305`），损坏的 workbook.xml 会在自解析 fallback **之前**直接打死整个转换。

**修复方向**：`if (localOff + 30 > n) return null;`，读出 ln/le 后再 `if (localOff + 30 + ln + le + compSize > n) return null;`。

### 1.6 OLE2 一律报 `.doc`，`.xls/.ppt/.msi/加密 OOXML` 被误导（P3）

**位置**：`src/sniff.js:88`（任何 OLE2 → `type:'doc'`）、`src/convert.js:68`（文案「老版 .doc（Word 97-2003）…另存为 .docx」）

**实测**：512B OLE2 魔数文件命名 `book.xls` → 提示另存为 `.docx`。OLE2 是 .doc/.xls/.ppt/.msi/.msg/加密 OOXML 的公共容器。

**修复方向**：改通用文案（「老版 Office 二进制格式（.doc/.xls/.ppt）或加密文档暂不支持…」），或按 OLE2 目录流名细分（WordDocument / Workbook / PowerPoint Document / EncryptedPackage）。

### 1.7 `meta.backend` 标签失真（P3）

`src/xlsx.js:272` 自解析路径也返回 `backend: 'read-excel-file'`（注释称「保持契约枚举」）。meta.backend 已无法区分实际引擎，调试/契约二分困难。建议新增 `'xlsx-self'` 或把契约枚举扩为 `'read-excel-file' | 'xlsx-self'`（改动需同步 architecture §2 与 C 组断言口径）。
