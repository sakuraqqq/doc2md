## 2. 内存口径（**必须连缺陷一起引用**）

**口径**：`Get-Process msedge` **全部进程** `WorkingSet64` 之和，**250 ms** 采样；基线 = 前 20 样本中位数；增量 = 峰值 − 基线。

**已知偏差（三条，逐条列明）**：

1. **跨进程共享页被重复计入** ⇒ 总和 **大于**真实物理占用；
2. **含 DSH GUI 自身的浏览器进程**（基线已扣，但其自身波动会混入）；
3. **工作集不会及时回收** ⇒ 峰值可能"记住"了更早的分配。

⇒ **可信区间是"量级"，不是精确值。** 但即便按 3× 高估折算，增量仍有 **≈2.4 GB**，相对 200 MB 的上界是 **12× 以上**的量级差 —— **结论不依赖口径之争**。

**为什么不用页内采样**：实测**解析完全阻塞主线程** —— 50 ms 间隔的页内 `setInterval` 在 55 s / 99 s 的转换里**只命中 2 次**（`samples: 2`）。
⇒ **页内采不到尖峰**（这是本轮把内存采样改到 Node 侧的直接原因）。

## 8. ⭐ 口径改良复测（2026-09-18 晚 · 用户拍板「D4 口径统一到 PSS」后）

> **缘起**：用户拍板 **D4 口径与上界按建议重定**（口径统一到 **PSS**，与手机同源）。
> ⚠️ **WSL2 这条路由会话内不可达**：实测 `wsl.exe --status` → `Wsl/EnumerateDistros/Service/E_ACCESSDENIED`（**WSL 服务层拒绝，非 harness 沙箱标记**）⇒ **Linux 的 `/proc/<pid>/smaps_rollup` PSS 本轮仍缺**（如实登记）。
> ⇒ 改用**当时可得的最佳代理口径**：**`PrivateMemorySize64` 之和**（私有提交字节）—— **不重复计入共享页**，且大堆是私有的 ⇒ **≈ PSS 减共享分摊**。

### 8.1 双口径结果（同一批大档重测）

| 档 | 耗时（本轮） | **WS 求和**（旧口径） | **Priv 求和**（新口径 ≈PSS） |
|---|---|---|---|
| `4-mid-large` 35.9 MB | **66,710 ms** | 基线 2,837.5 → 峰值 9,223.1（**+6,385.6 MB**） | 基线 3,492.7 → 峰值 9,983.9（**+6,491.2 MB**） |
| `3-big` 47.4 MB | **69,336 ms** | 基线 6,931.1 → 峰值 10,419.6（+3,488.5 MB） | 基线 7,655.0 → 峰值 **12,317.7 MB**（+4,662.7 MB） |

**两条结论**：
1. ✅ **旧口径没有被共享页显著放大** —— 新口径的增量（+6,491 MB）**比旧口径还略大**（+6,386 MB）。⇒ **§0–§3 的量级结论不变，且更稳**。
2. ⚠️ **但第 4 档的"增量"不可用**：它的**基线被第 3 档的残留污染**（基线 WS 2,838 → **6,931 MB**，Priv 3,493 → **7,655 MB**）—— Web 进程的工作集/私有提交**不会在页重载后归还**。⇒ **背靠背连跑时，可比的是"绝对峰值"，不是"增量"**。
   - **修法（下次照做）**：**每档之间重启浏览器窗口**（或用 `chrome_close` → `chrome_open`），让基线回到干净值；否则只能引用绝对峰值。

### 8.2 顺带发现：同档耗时波动很大（**不可当稳定指标**）

同一档、同一构建、同一台机：

| 档 | 第 1 次 | 第 2 次 | 第 3 次 |
|---|---|---|---|
| `4-mid-large` | **55,187 ms** | 58,277 ms | **66,710 ms** |
| `3-big` | **98,631 ms** | — | **69,336 ms** |

⇒ **同档波动可达 1.4×**（机器热状态/占用不同）。**md 产物四次全部逐字节相同**（339,912 / `F90DCE36…`；352,029 / `C2C41F5A…`）—— **产物确定，耗时不确定**。
⇒ 对 Y3 的影响：门槛 5 s vs 实测 55–99 s，**余量 11–20×，波动不改变先红结论**；但**日后比对耗时必须同批同机同温**，不能跨批相减。

### 8.3 与手机 T3 的对照（**口径不同源，只作量级参照**）

- 手机 T3（冷态）：`4-mid-large` 渲染进程峰值 **≥7.50 GiB**；
- 本轮桌面：**全部 msedge 进程私有提交之和**峰值 **9,984 MB ≈ 9.75 GiB**，其中**含 DSH GUI 自身的浏览器进程**（基线里就有 ≈3.5 GB）。
- ⇒ **两者不是同一个量**（单渲染进程 PSS vs 全浏览器私有提交之和，且基线构成不同）⇒ **不可直接相减**。唯一稳的说法：**桌面与手机在同一量级（数 GB～十数 GB）**。

## 9. ⚠️ 更正（2026-09-18 晚 · **本报告 §0/§3 与交接文档 A11.21 的一处误读**）

**我读错了 D4 的列语义，并因此下了一个错误结论。在此更正，原文保留以留痕。**

### 9.1 误读一：把「目标」当成了「现状上界」

`docs/大文件路径专项-验收判据-20260917.md` 的 D4 行是四列 **`判据 | 判据形式 | 现状 | 目标`**：

- **现状** = 手机 12.63 GiB
- **目标** = **< 200 MB（桌面）**

⇒ **200 MB 是"修完之后要打到"的目标值**，**不是**"现状不得超过的上界"。
⇒ 因此 **§0/§3 里"200 MB 被撞破约 37× ⇒ 该数作废"的说法不成立** —— 现状超标**正是这次要修的东西**，拿现状去否证目标，是**循环论证**。

### 9.2 误读二：口径与 D4 指名的**不是同一个量**

- **D4 指名口径**：页面内 `performance.measureUserAgentSpecificMemory()` —— 量的是**页面自身**（JS 堆 + DOM + worker）。
- **本报告口径**：**全部浏览器进程** `WorkingSet64` / `PrivateMemorySize64` 之和 —— 含**浏览器自身的固定开销**（本轮基线就有 **2.8–3.5 GB**）。
- ⇒ **两者相差的是浏览器底座**，**不能互相判定**。本报告的数字**不能用来给 200 MB 定生死**。

### 9.3 那么本报告的数字还有用吗？—— 有，但要重新定位

| 用途 | 是否成立 |
|---|---|
| 量化「**现状有多糟**」（修前基线，供修后对照） | ✅ **成立**：大档增量 **+6.4–7.4 GB**，量级远超任何 MB 级目标 ⇒ **修前基线可用** |
| 证明「**小档地板**很低」（即 200 MB 目标可达） | ⚠️ **尚未做对**：小档 22–25 ms 完成，**峰值低于采样分辨率**；且本口径含浏览器底座 ⇒ **必须改用 D4 指名 API 重做** |
| 否证「200 MB 作为目标」 | ❌ **不成立**（见 9.1/9.2） |

### 9.4 ✅ 该补的那一步：**已补做（同日）—— 地板测试通过，200 MB 目标站得住**

1. 给本地站点加 **`Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp` + `Cross-Origin-Resource-Policy: same-origin`** ⇒ 实测 **`crossOriginIsolated === true`** ✅；
2. 页面内调 **`performance.measureUserAgentSpecificMemory()`**（D4 指名口径）取快照：

| 状态 | 页面总内存 | 主要构成 |
|---|---|---|
| **空载基线** | **5.72 MB** | JavaScript 4.64 / Shared 1.03 / DOM 0.04 |
| `1-small` 154 KB 转完（16 ms） | **6.10 MB** | JavaScript 4.63 / Shared 1.44 |
| `2-mid` 773 KB 转完（23 ms） | **6.61 MB** | JavaScript 4.79 / Shared 1.79 |
| 两档都转完 | **6.62 MB** | JavaScript 5.21 / Shared 1.36 |

⇒ ⭐ **地板 = 6–7 MB 量级，离 200 MB 目标差约 30 倍** ⇒ **"200 MB 会不会被小档就撞破"的答案是：不会。**
⇒ **D4 的目标值（页面 < 200 MB）在小档侧完全站得住**；剩下的只是**大档修完（流式）之后**能否同样回到这一量级 —— 那要等实现后再测。
3. ⚠️ **大档仍无法在转换中取快照**（主线程阻塞，见 §2）⇒ 该口径的大档"峰值"**只能等流式实现之后再测**（那时转换够快，快照可得）。**这也是先红阶段不需要它的原因**。
