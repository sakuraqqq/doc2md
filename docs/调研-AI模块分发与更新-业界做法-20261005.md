## 0. 一句话

分发与更新的三件事上，业界**早有成熟形状**：**清单（manifest）** 用"摘要 + 类型 + 分层"描述制品（OCI/model-spec）· **更新** 用"签名元数据 + 防回滚/防冻结/防混搭"的框架（TUF）· **落地存放** 用"持久目录 vs 缓存目录"的官方语义（Android）。
⭐ **⇒ 本设计不发明新协议**：清单字段照 OCI 的"摘要寻址"思路裁剪，更新的验收面照 TUF 的攻击清单写，存放语义照 Android 官方文档判。

## 2. 读到的三条，各自给了我们什么

### 2.1 model-spec（OCI）：清单长什么样

- 制品类型用 `artifactType` 显式声明（模型清单 = `application/vnd.cncf.model.manifest.v1+json`）；
- **配置与权重分开**：`config` 按 **digest** 引用，权重放 `layers`；
- **层**用 `mediaType` 表达压缩/打包形态（raw / tar / tar+gzip / tar+zstd）；
- 多权重文件 ⇒ **拆成多层**。
⭐ **对我们的含义**：清单必须**摘要寻址**（每个可下载物都有 `sha256`），且**描述与数据分离** —— 这正是 `A2` 字段表要的形状；我们**不需要** OCI registry（I2 已定 GitHub Releases），只需"**清单 + 若干资产**"。

### 2.2 TUF：更新的负面验收面（9 条攻击）

- **回滚**（装上比已知更旧的版本）· **fast-forward**（把版本号吹到未来，让后续更新永远"像回滚"）· **无限冻结**（一直给旧元数据而客户端不知道）· **混搭**（拼出从未同时存在过的元数据组合）—— ⭐ **这四条直接落在我们要写的规则里**：清单**单调递增**、**拒绝更旧**、**撤销要可达**、**更新失败要能被察觉（⛔ 不静默）**；
- TUF 还给了两句"世界观"：① 能改你流量的人**总能 DoS** ⇒ 目标不是"永远能更新"，而是"**攻不进来 + 失败可见**"；② **不要在环境里假设一定有 TLS**（它的设计不依赖 TLS）。
⭐ **对我们的含义**：④ 更新策略的判据写成"**拒绝更旧 + 撤销可达 + 失败可见**"三条，而不是"下载成功就算过"。

### 2.3 Android 应用专属文件：⑤ 的直接依据

- **持久 vs 缓存**是两个目录（`filesDir` / `cacheDir`），两者**卸载即清**；
- ⚠️ **缓存目录可能被系统提前清**（"当设备的内部存储空间不足时，Android 可能会删除这些缓存文件以回收空间。因此，请在读取前检查缓存文件是否存在"）；
- 可查 `getCacheQuotaBytes()`；官方还明说 **"即使 Android 有时会自行删除缓存文件，你也不应依赖系统为您清理这些文件"**；
- 内部空间"**通常比较小**"，写之前应**先查询可用空间**。
⭐ **对我们的含义**：权重**必须**进持久目录；**可重建**的东西（清单副本、ETag）才放缓存目录；**下载前先查空间**；**"系统会替我清"是错的假设**。

## 5. 自创项标注（`prior-art-first` 铁律 1）

- ⭐ **本调研涉及的机制，没有一项是本设计自创的**：清单形状借 OCI、更新验收面借 TUF、存放语义照 Android 官方。
