## 1. 已实测确认的 bug

以下现象均在当前 HEAD 用系统 Edge（headless）调用 `window.__doc2md` 实测得到，不是纯静态推断。

### 1.1 HTML→Markdown 行内拼接注入多余空格（P0）

**现象（实测输出）：**

| 输入 HTML | 当前输出 |
|---|---|
| `<p>Hello <b>world</b>.</p>` | `Hello **world** .` |
| `<p>这是<b>重点</b>内容。</p>` | `这是 **重点** 内容。` |
| `<p>The <em>quick</em> brown fox <code>jumps</code>.</p>` | `The *quick* brown fox `jumps` .` |

中文加粗会被空格撑开成“重 点”，英文会在标点前多一个空格，属于可见的**内容性错误**。

**根因**：`index.html` 的 `htmlToMarkdown`（约 205–274 行）把文本节点、`<strong>`、`<em>`、`<code>`、`<a>` 等分别 push 进数组后统一 `out.join(' ')`。原 HTML 里没有空格的地方也被强行插入一个空格；随后的清理只处理中文标点前的空格（` +(?=[，。；：！？、）】」』])`），不处理 ASCII 句点、逗号、括号，也不处理中文文字与行内标记之间的问题。

**影响面**：TXT/HTML 与 DOCX（mammoth → HTML → 同一函数）两条主链路都受影响，是最常见的“第**一**章”“**重点**内容”类富文本。

**契约为什么没拦住**：C 组断言只查“关键 token 存在”（如 `DOC2MD-DOCX-OK-2026`），不校验精确空白与行内结构，这类错误会全绿通过。

**建议方案**：
1. 去掉全局 `out.join(' ')`，块内按“是否需要空格”决定拼接，而不是一律加空格。
2. 推荐重构为“段落级构建”：`walk` 不再把 token 推进同一个全局数组，而是把相邻的文本/行内元素按原始顺序拼接，只做两件事：
   - 每个文本节点内部按原样保留空白（首尾空白在块边界才 trim）；
   - 行内标记（`**`、`*`、`` ` ``、`[ ](...)`）直接贴靠原文本，不自行补空格。
3. 若要保持“英文单词间必须有一个空格”的容错（例如 `<b>world</b><br>` 场景），用相邻字符规则判断：前一个是 `[A-Za-z0-9]` 且后一个是 `[A-Za-z0-9]` 时才补一个空格；CJK 相邻不补；标点前不补。

**回归用例建议**（加入 C 组/独立快照测试）：
```html
<p>Hello <b>world</b>.</p>
<p>这是<b>重点</b>内容。</p>
<p>The <em>quick</em> brown fox <code>jumps</code>.</p>
<p>第<b>一</b>章 概述</p>
```

### 1.2 列表／表格／引用／锚点用 `textContent` 抽取，结构信息丢失（P0）

**现象（实测输出）：**

| 输入 HTML | 当前输出 | 问题 |
|---|---|---|
| `<ol><li>one<ol><li>1.1</li><li>1.2</li></ol></li><li>two</li></ol>` | `1. one1.11.2\n2. two` | 嵌套列表被展平、子项粘连 |
| `<ul><li><b>加粗项</b> 与链接 <a href="https://x">链接</a></li></ul>` | `- 加粗项 与链接 链接` | 行内加粗/链接丢失 |
| `<blockquote><p>第一段</p><p>第二段</p></blockquote>` | `> 第一段第二段` | 多段落合并成一行 |
| `<table>…<td><b>重点</b> A<br>B</td>…` | `重点 AB` | 单元格内加粗丢失、换行消失 |
| `<a href="https://x/y.png"><img src="z.png" alt="图"></a>` | `[](https://x/y.png)` | 锚包图片变成空链接 |
| `<h1>A<br>B</h1>` | `AB` | 标题内换行丢失 |

**根因**：`index.html` 里以下位置直接取 `textContent`，跳过了子节点的行内结构：
- UL/OL/LI（约 225–235 行）
- BLOCKQUOTE（约 239 行）
- TABLE 单元格 `tableToMd`（约 276–292 行）
- 锚点（约 247–251 行）

对 DOCX 尤其致命：mammoth 输出的表格、列表、引用在真实文档里常含加粗/斜体/超链接，当前都会退化成纯文本。

**建议方案**：
1. **列表**：改为递归处理。`UL/OL` 内只处理直接子 `<li>`；每个 `<li>` 用子节点 walker 生成行内 markdown；遇到嵌套 `UL/OL` 再递归缩进。保留 `OL` 的 `start` 属性与递增序号。
2. **表格**：单元格内容走子节点 walker，得到行内 markdown 后再做 GFM 转义（`|`、换行）；单元格内 `<br>` 转成空格或保留 `<br>` 语义（建议按空格处理并在文档注明）；`rowspan/colspan` 至少检测并补空位或给出 warning（v1 可先声明不支持合并单元格）。
3. **引用**：块级子元素（P/DIV 等）逐个处理，每一行都加 `> ` 前缀，而不是整体 `textContent` 一次。
4. **锚点**：当 `<a>` 内只有图片时，输出 `[![alt](src)](href)`；文本优先时按现有规则。
5. **标题**：`<br>` 视为软换行，不吞掉。

### 1.3 嗅探与架构声明不符：PDF 前置垃圾字节未兜底、二进制被当文本转换（P0）

**实测：**
- 输入 `junk:%PDF-1.4\n`（垃圾前缀 + 合法 PDF 头）→ `sniff` 返回 `text`；
- 输入 `MZ...`（exe 魔数）→ `sniff` 返回 `text`，随后按 UTF-8 解码成乱码并显示“转换成功”。

**与架构冲突**：`docs/architecture.md` §3 明确写“PDF：再兜底『偶有前置垃圾字节』，搜首个 `%PDF` 出现位置 ≤1024”；并举例“exe 改名 .docx → 判 unknown”。当前 `index.html` 的 `sniff`（约 181–201 行）只判断 `startsWith('%PDF')`，且没有“未知二进制”检测，未知一律落到 `text`。

**建议方案**：
1. PDF：在前 1024/64KB 内搜索 `%PDF`，命中即判 `pdf`（与架构对齐）。
2. 在回落到 `text` 之前增加二进制启发式：对头部采样，统计 NUL 字节与控制字符（`<0x09/0x0A/0x0D` 之外 `0x00–0x08`、`0x0E–0x1F`）占比；占比高 → 返回 `unknown`（detail: `binary`），UI 显示“无法识别的文件类型”。
3. 注意顺序：BOM 的 UTF-16 文件含大量 NUL，必须先按 BOM 判定为文本，再做二进制启发式。
4. 补充契约样例：垃圾前缀 PDF、改名 exe、改名普通 zip、纯乱码文件，断言都给出友好错误而非乱码 Markdown。

### 1.4 GBK/GB18030 中文文本与 HTML 乱码（P1）

**实测：** GBK 字节 `中文测试` 经 `convert()` 得到 `���Ĳ���`（UTF-8 容错解码产物）。

**根因**：`decodeText`（`index.html` 约 165–178 行）只支持 UTF-8/UTF-16LE/UTF-16BE，没有 BOM 时一律按 UTF-8 解码。中文环境里无 BOM 的 GBK/GB18030 `.txt`、`.html` 非常常见。

**建议方案**：
1. 对 HTML：先取原始字节前 4KB 用容错 UTF-8 解码，正则查 `<meta charset="gb2312|gbk|gb18030|big5"` 等；命中则用 `new TextDecoder('gb18030')` 重新解码整份文件（浏览器原生支持该 label，不引依赖）。
2. 对纯文本：先用 `TextDecoder('utf-8', { fatal: true })` 试解前 4KB；抛错或替换字符占比过高时回退尝试 `gb18030`，再不行按 UTF-16/原样。
3. 在 README 支持矩阵中同步说明“自动识别 BOM / UTF-8 / UTF-16 / 常见 GBK 无 BOM 文本”。

### 1.5 xlsx 的 `meta.truncated` 契约字段从未置真（P1）

**现象**：`convert()` 初始化 `meta.truncated = false`（`index.html` 512 行），转换器返回后没有同步；xlsx 转换器内部算了 `truncated` 并写进 warning（约 469–482 行），但 `meta.truncated` 永远为 `false`，与 `docs/architecture.md` §2 的接口契约不一致。

**附带问题**：截断提示文案为“全簿共 N 行”，但 `totalRows` 只累加了**已读取**的前 5 个 sheet；当 sheet 数超过上限时，未读取 sheet 的行数不计入，数字会偏小、语义错误。

**建议方案**：
1. 转换器统一返回 `{ markdown, warnings, truncated }`，`convert()` 里执行 `meta.truncated = !!res.truncated`。
2. 把提示文案改成“已读取前 5 个 sheet 共 N 行”，或在读取前先用 sheet 元数据统计总行数（代价高，非必须）。
3. 契约测试加一条：构造 >5 sheet 或 >1000 行的 xlsx，断言 `meta.truncated === true`。

## 2. 与既有 backlog 重合、已确认属实的高危项

以下内容在 `docs/doc2md-手机端找茬验证清单.md` 与 `docs/RELEASE.md` v0.1.1 backlog 中已有记录，本次审查确认代码现状与记录一致，摘录并补方案，避免遗漏。

### 2.1 OCR `corePath` 伪造域名（P1，红线相关）

`index.html` 344 行传 `corePath: 'https://doc2md.local/tesseract-core/'`，依赖 BLINE patch 在 worker 里拦截 `importScripts('tesseract-core…')` 重定向到本地 blob。任何漏匹配、tesseract.js 升级、WebView 行为差异都会真的去请求 `doc2md.local`，轻则 console error（违约 C2），重则动摇“零外发”。

**建议方案**：
1. 首选：`corePath` 改为基于当前页面的同源绝对 URL，例如 `new URL('./vendor/', location.href).href`。现在 vendor 已经是同源分文件（红线 2 已允许），worker 也是页面同源 blob，直接让 worker `importScripts` 同源绝对路径即可，不必再经过伪域名；patch 可退化为“仅当 URL 指向外域时抛错”的双保险。
2. 保留现有 patch 并加白名单断言：`url` 的 origin 必须等于 `self.location.origin`，否则拒绝并给出可读错误。
3. 上线前必须在 Chromium + 至少一种 Android WebView 实测 OCR 首次与二次离线，且 Network 面板零外域。

### 2.2 SW 全量预缓存约 18MB，手机首载过重（P1）

`sw.js` PRECACHE 包含两个 wasm core（各约 3.95MB）与 eng/chi_sim 语言包（约 7.4MB）。实际只按 SIMD 支持加载一个 core，且多数用户不转 OCR。

**建议方案**：
1. PRECACHE 只保留应用外壳：index、manifest、图标、mammoth、pdf.js 及 worker、read-excel-file、tesseract 主库与 worker 入口（不含 core 与语言包）。
2. core/语言包改为运行时缓存：SW 现有 cache-first miss 时写入逻辑已经具备，首次 OCR 在线下载后自然离线可用。
3. 首次 OCR 前在状态区提示“首次 OCR 需下载约 X MB（此后离线可用）”，避免“正在处理…”长时间无反馈。
4. 若必须保证“装完即全功能离线”，可做成二段式：安装完成 app 外壳后，再后台低优先级缓存 OCR 资源；失败不阻塞 SW 安装（`Promise.allSettled`），并给出“离线 OCR 包未就绪”提示。

### 2.3 扫描 PDF 逐页 scale:2 渲染 + OCR，手机内存/耗时风险（P1）

见 `index.html` 375–402 行（`ocrPdfToMarkdown`）与手机找茬清单 #3。补充两点：
- 现在判定“全书文本量 <10 字符”才整本走 OCR；混合型 PDF（前几页有文本层、后几页是扫描图）会整本走文本层，扫描页输出空白。建议改为**逐页判断**：单页文本量过低的页才 OCR，其余页直接取文本层。
- OCR 全程没有进度反馈，建议用 tesseract worker 的 progress 事件回填 `#status`。

### 2.4 docx 图片 base64 内嵌，产物膨胀且提示文案错误（P1）

代码 warning 文案是“已忽略 N 个内嵌图片”，但 mammoth 默认把图片以 `data:` URI 内嵌，实际没有忽略；架构 §4.2 的“mammoth 默认忽略图片”描述也与实现不符（README/DD 中已记录真实文档 3KB 正文 / 204KB 文件的现象）。

**建议方案**（与 v0.1.1 backlog #1/#2 合并）：
1. 先修文案：不传 `ignoreImages` 时如实提示“已内嵌 N 个图片（data URI）”；若决定丢弃，用 `convertImage` 返回空并提示“已忽略”。
2. 中期做“图片抽出”：mammoth 自定义 `convertImage`，把图片按 `assets/<docname>-<序号>.<ext>` 写出，Markdown 用相对路径 `![](assets/…)`；下载时同时产出 zip（markdown + assets）或逐文件下载。备选：小于阈值（如 100KB）内嵌，大于阈值抽出，避免小图也拆包。
3. `alt` 处理按 v0.1.1：优先文件题注/文件名，其次空 alt，不要把 Word 的“图片包含 室内……”AI 描述照搬。

## 3. 其它可优化点（P2）

### 3.1 UI / 可访问性
- **键盘可达**：dropzone 是普通 `div` + click（`index.html` 655 行），建议加 `role="button"`、`tabindex="0"`、`aria-label`，并支持 Enter/Space 打开文件选择；PWA audit 的 48 项未覆盖键盘。
- **忙碌状态**：转换（尤其 OCR）进行中仍可再拖文件触发并发任务；建议转换期间锁定拖放/按钮，或在队列里显式排队。
- **进度**：只有“正在处理 N 个文件”，无单文件/单页进度，也无取消按钮。
- **完成文案**：即使全部失败也显示“完成：共 N 个文件”，建议显示成功/失败计数。
- **结果区只增不清**：连续转换后页面无限堆积；建议提供“清空结果”按钮或单卡删除。

### 3.2 OCR / 图片
- 图片 OCR 直接送原图（`registry.image`，约 485–494 行），不降采样；50MB 上限内的大图在手机上仍有 OOM 风险。建议先按最长边（如 3000px）等比降采样为 JPEG 再识别，并在 UI 显示降采样提示。
- 空白/低置信度结果已有 warning，但 PDF 的 OCR 降级路径没有透出置信度；建议统一。

### 3.3 文案与文档不同步
- `index.html` 107 行徽标仍写“⚡ 离线可用 · 单文件”，T9′ 后已是“单目录离线”（index + vendor/ + langs/）；footer 版本“v0.1”未跟上 v0.1.0。
- `docs/architecture.md` §8.2 写导航“cache-first”，但 `sw.js` 实际是“网络优先、离线回退”的 v2 修复（53–66 行），文档未同步。
- 1.2.4 提到的“mammoth 默认忽略图片”描述错误。

### 3.4 SW 与缓存维护
- vendor 文件名固定 + 资源 cache-first：日后升级 mammoth/pdf.js 若忘记 bump `CACHE_NAME`，旧资源会一直命中缓存。建议发布时把 vendor 版本并入文件名（如 `pdfjs-3.11.174.min.js`）或在 RELEASE-CHECKLIST 加“bump CACHE_NAME”硬检查。
- `cache.addAll` 任一资源失败会导致整个 SW install 失败；配合 2.2 的分段缓存一并处理。

### 3.5 测试覆盖
- 现有契约主要断言“关键 token 存在”，无法发现 1.1/1.2 这类空白与结构回归。建议新增“精确输出快照”用例（不依赖浏览器渲染差异的纯函数断言）：
  - 行内加粗/斜体/代码相邻中英文、ASCII 标点；
  - 嵌套 ul/ol、li 内行内格式、表格内加粗与 `<br>`、多段 blockquote、锚包图片、标题内 `<br>`；
  - sniff：垃圾前缀 PDF、exe 改名、普通 zip、空文件、UTF-16/GBK 文本；
  - xlsx：`meta.truncated` 为真的场景。
- 快照文件进入 `tests/data/` 并字节锁，与现有 B 组流程一致。
