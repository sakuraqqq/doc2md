# doc2md v0.1.9（2026-09-16）

> 本版修一个 **P1 静默错**：某些 PDF（典型是 **WPS 导出**）转出来的文字**字符全对、顺序却乱**，而且界面**没有任何提示**。完整发布记录见 `docs/RELEASE.md` 的「## v0.1.9」节。

## 修什么

**症状**：WPS 导出的 PDF 转成 Markdown 后，**字都对，但顺序错** —— 公务号 `学工〔2026〕151号` 会变成 `学26〕1号05工21〔`（同一视觉行的两段文字互相交错），严重时**多行被拍平成一行**。全程**无警告、无报错**，用户拿到的是「看起来像正常文字、其实顺序全乱」的结果。

**根因**：这类 PDF 用「**文本空间坐标**」排版 —— `Tm`（文本矩阵）带缩放、逐字用 `TD` 推进。旧实现把文本空间的**位移量当成页面坐标直接累加**，于是同一视觉行内不同文本对象的横向尺度不一致 ⇒ 排序错乱（对照：Chromium 打印的 PDF `Tm` 缩放恒为 1，**从来不受影响** —— 这也是它长期没被发现的原因）。

**修复**：让**缩放参与计算** —— 有效字号 = `字号 × 缩放`；位移与行距按缩放折算（`src/pdf.js`，5 处）。

## 兼容性（重要）

- **既有正常 PDF 的输出逐字节不变** ✅：契约样例 10 份 + 真机 Chromium 打印 PDF + 软著 PDF 全部**逐字节相同**（跨机独立复核：`相同 10 · 变化 1 · 违规 0`，退出码 0；唯一「变化」的是本版新增的缺陷样例，它本来就该变）。
- **顺带修好第二个受害者**：一份真实的期刊论文 PDF（同为「逐字 + 缩放」形态）此前输出里也含交错串；本版输出分行正确，其可读性判据（CJK 数 / 占比 / 三个高置信子串）依旧全部通过。
- 只改 **PDF 文本层坐标计算**；嗅探 / DOCX / XLSX / 图片 OCR 逻辑**未动**（`vendor/`、`langs/` 零改动）。

## 验证

- 契约 **256 tests / 254 pass / 0 fail / 2 skip**；新增契约组 U **U9**：同一视觉行由两个文本对象拼成时，行内顺序必须按书写顺序（**去空白后比对**，空格受字体度量影响不作判据）
- **负对照（决定性）**：把实现切回修复前 → **U9 必红**（跨机独立复现，连乱码串 `OSTNEHWECIOORNDDLLIINNEE` 都逐字相同）⇒ 断言确实在守
- **独立验收（Linux 侧，真 chromium）五项全绿**，含 **V-4 渲染基准**（把样例渲染成图目视确认期望值非自证）与 **V-5 换数据**（用自造的、参数不同的 PDF 复测：旧产物把三行拍平成一行 → 新产物三行正确）
- lint 0 · metrics 超限 0 · PWA 48/48 · 离线 OCR PASS(93%)
