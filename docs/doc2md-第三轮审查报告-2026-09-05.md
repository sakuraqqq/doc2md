## 1. 新确认的 Bug（按影响排序）

### 1.1 成功转换的 `meta.elapsedMs` 恒为 0（P1）

**位置**：`src/convert.js:52-77`（成功路径 `return` 在 74 行）；连带 `src/ui.js:96`、`tests/contract_v1.test.mjs:306-309`

**根因**：`convert()` 开头创建的 `meta` 对象带初始值 `elapsedMs: 0`（56 行）。耗时只在错误路径的 `done()` 闭包里计算（58 行 `{ ...meta, elapsedMs: Math.round(performance.now() - t0) }`），而**成功路径 74 行直接 `return { markdown: res.markdown || '', meta, error: undefined }`，返回的是未经修饰的原 `meta`**，`elapsedMs` 从未被赋值。错误路径反而有正确耗时——只有失败的卡片显示时间。

```js
// src/convert.js:68-77
try {
  const res = await registry[s.type](file, buf);
  meta.backend = res.backend || null;
  meta.warnings = ...;
  meta.truncated = ...;
  // ← 缺 meta.elapsedMs = Math.round(performance.now() - t0);
  return { markdown: res.markdown || '', meta, error: undefined };  // elapsedMs 仍是 0
} catch (e) {
  return done({ error: ... });  // done() 才计算 elapsedMs
}
```

**影响面**：
- UI 层 `src/ui.js:96` 用 truthy 判断 `result.meta.elapsedMs ? ' · ' + ms : ''`，0 为 falsy → **所有成功转换的耗时显示被静默吞掉**；用户永远看不到「转换用时」这个产品声称的反馈。
- 契约测试 306-309 行 `if (typeof res.meta.elapsedMs === 'number')` 恒真，日志打出「转换 0ms（外部计时 XXms）」自相矛盾的输出（测试断言本身用外部计时，不受影响——这也是它没被测出的原因）。
- `docs/architecture.md` §2 契约声明「meta.elapsedMs 为转换耗时」，成功路径实际违反契约。

**修复**（一行）：成功分支 return 前加 `meta.elapsedMs = Math.round(performance.now() - t0);`，或统一改走 `done()` 风格。

**回归用例建议**：C 组任一成功用例断言 `res.meta.elapsedMs >= 0 && res.meta.elapsedMs > 0`（或至少 `!== 0`），并在 M 组断言卡片 meta 文本含 `ms` 字样。

### 1.2 OMML 括号 `m:d` 内容一律拍平为纯文本，且无退化警告（P1）

**位置**：`src/docx.js:95-100`（`d` 分支）+ `src/docx.js:106-110`（`ommlConcat` 传 `df=null`）

**根因**：`ommlParts` 的分支表覆盖 `t / r / oMath / oMathPara / f / sSup / sSub / sSubSup / rad / d`，**唯独没有 `m:e`（base 元素）的处理器**。`rad`、`f`、`sSup` 等分支都正确地先 `ommlChild(el, 'e')` 取子元素再 `ommlConcat(子元素)`（遍历的是 `m:e` 的**子节点**，结构正常递归）；唯独 `d` 分支写成了 `ommlConcat(el)`——遍历 `m:d` 自己的子节点（`m:dPr`、`m:e`），`m:e` 落进兜底分支被当成「复杂结构」整体取 `textContent`：

```js
// src/docx.js:95-100 —— d 分支（括号）
if (ommlIs(el, 'd')) {
  const lc = el.getAttribute('m:begChr') || ... || '(';
  const rc = el.getAttribute('m:endChr') || ... || ')';
  parts.push(lc + ommlConcat(el) + rc);   // ← el 是 m:d，其子 m:e 无处理器 → textContent 拍平
  return;
}

// 对比 rad 分支（正确写法）：ommlChild(el, 'e') 先取 m:e，ommlConcat 遍历 m:e 的子节点
```

且 `ommlConcat`（106-110 行）对每个子节点调用 `ommlParts(c, parts, null)`——**`df` 传 `null`，兜底分支的 `df.degraded = true` 被吞**，连「N 个复杂公式已按纯文本保留」的 warning 都不会触发。

**现象**（括号内嵌套任何结构即触发）：

| Word 公式（OMML 结构） | 期望输出 | 实际输出 |
|---|---|---|
| `m:d > m:e > m:f(a, b)`（括号内分数） | `(\frac{a}{b})` | `(ab)` |
| `m:d > m:e > m:sSup(x, 2)`（括号内上标） | `(x^{2})` | `(x2)` |
| 二项式系数、绝对值等一切「括号包结构」 | 结构化 LaTeX | 纯文本粘连 |

**契约违背**：文件头注释明确「复杂结构 v1 退化 = 提取全部文本按纯文本保留 + **warning**」。本条是**静默降级**（无 warning），比声明的退化口径更差；且 `m:d` 是已实现分支（专门处理了 begChr/endChr），内容却全部拍平，等于这个分支只对「纯文本括号」有效。

**修复**（两处）：
1. `d` 分支改为与 `rad` 一致：`const e = ommlChild(el, 'e'); parts.push(lc + (e ? ommlConcat(e) : '') + rc);`
2. `ommlConcat` 增加 `df` 参数并透传：`ommlParts(c, parts, df)`，让嵌套复杂结构的退化警告能冒泡。

**回归用例建议**：`tests/gen-samples.mjs` 增加「括号内含分数」样例（`m:d(begChr="(") > m:e > m:f`），断言输出含 `\frac{a}{b}` 且被括号包裹；再加一条「括号内积分」样例断言 degraded warning 出现。

### 1.3 `oMathPara` 含多个 `oMath`：第 2 个公式起内容丢失（P2）

**位置**：`src/docx.js:123-141`（`docxParseForMd` 的 oMath 循环）

**根因**：循环遍历文档中所有 `oMath`。对第一个位于 `oMathPara` 内的 `oMath`，父链上溯找到 `oMathPara` 后 `target = p`（整块替换、`block = true`），随后 `target.parentNode.replaceChild(r, target)` **把整个 `oMathPara` 连同其中其余 `oMath` 一起摘出文档**。同段的第二个 `oMath` 变成 detached 节点，被 124 行 `if (!om.isConnected) continue;` 跳过——**内容彻底丢失，连纯文本兜底都没有**，占位符也不会生成。

OMML 规范允许一个 `oMathPara` 包含多个 `oMath`（方程组、一行多式、从其他编辑器粘贴时常见）。单公式段落（绝大多数场景）不受影响，故降为 P2；但一旦触发即静默丢内容，用户无从得知。

**修复方向**：block 场景改为「先收集 `oMathPara` 下全部 `oMath`，逐个生成占位符（各自 `latex/rawText`，首个标记 block）后整块替换」；或最小改法——替换 `oMathPara` 前，把其中未处理的 `oMath` 的 `rawText` 以空格连接并入同一占位符。

**回归用例建议**：gen-samples 构造 `oMathPara > [oMath(A), oMath(B)]`，断言输出同时含 A、B 两个公式的内容。

### 1.5 输出无预览上限：50MB 输入护栏会被自己的输出击穿（P2）

**位置**：`src/ui.js:109-112`（`renderResult` 中 `ta.value = result.markdown`）；护栏定义 `src/convert.js:12`（`MAX_BYTES = 50MB`）

**根因**：输入侧有 50MB 护栏，但输出侧把**完整转换结果**直接灌进 `<textarea>`。一个接近护栏上限的 TXT（或文本层很厚的 PDF/DOCX）会产出同量级的 Markdown 字符串，`textarea.value` 赋值 + 布局渲染在几 MB 量级就会明显卡顿，几十 MB 基本假死——用户拖入一个「合法」文件，得到的不是转换结果而是死页面。多文件转换时 `results` 里还会累积多张大 textarea，进一步放大。

**修复建议**：
- 预览截断（建议 1MB）：textarea 只放前 N 字符 + 尾部追加「（预览已截断，完整内容请复制/下载）」提示行；
- 复制/下载按钮使用内存中的完整字符串（现在按钮回调读 `ta.value`，需改为闭包引用完整值）；
- `meta.truncated` 或 `meta.warnings` 通道现成可复用来提示截断。

**回归用例建议**：M 组加「大文本（>1MB）渲染不超时、含截断提示、下载内容完整」用例（可在浏览器用合成 File 构造，不必入库大样例）。

## 2. 边角 Bug / 健壮性（P3，按机会修）

### 2.1 `src/template.html` 尾部脏 markup（孤立 `</script>` + 10 行空行 + 过时文案）

template.html:130-131 是 fflate 内联脚本（`<script>` … `</script>` 闭合正常）；**147 行多出一个孤立 `</script>`**（无对应开标签），137-146 是 10 行空行。浏览器解析器会忽略孤立闭合标签，无行为影响，但 template.html 是「唯一源码真相」，脏 markup 会原样进入每次构建产物。另外 **footer（134 行）文案「内联 mammoth v1.12.2」已过时**——T9′（DD-15）后 mammoth 是 `vendor/` 同源分文件，不再内联。建议删除 137-147 的空行与孤立标签，footer 文案同步为「同源分文件 vendor/」。

### 2.2 xlsx sheet 名含 `"` 时整个转换失败（实体解码顺序错误）

**位置**：`src/xlsx.js:54-59`（`xlsxSheetNames`）

先对整段 XML 做 5 个命名实体的全局解码，**再**跑 `name="([^"]*)"` 正则。sheet 名含双引号（Excel 中合法，如 `报表"1"`）时，XML 里的 `&quot;` 先被解码成 `"`，正则在第一个引号处截断 → 捕获到错误名 `报表` → `readXlsx(ab, {sheet: '报表'})` 找不到 → **整个文件转换失败**。复审报告 §1.8 提的是「数字实体不解码」（内容残留），本条是修复时**新引入的顺序问题**（直接报错，更严重些）。修复：先正则捕获原始值，再对**捕获值**解码。低频但中文用户起 sheet 名带引号并不罕见。

### 2.3 `zipEntry` 遇损坏文件可抛 RangeError，违背「解析失败回退单 sheet」的注释承诺

**位置**：`src/xlsx.js:31-33`

中央目录的 `localOff`（32 行读取）未做边界校验就 `dv.getUint16(localOff + 26, true)`（31 行）。损坏/恶意构造的 xlsx 让 `localOff` 越界时，DataView 直接抛 RangeError；51 行注释声称「解析失败即回退单 sheet」，实际异常会一路上抛 → `convert()` 顶层 catch → 用户看到「转换失败」而非单 sheet 回退。修复：读 local header 前校验 `localOff + 30 + ln + le <= n`，越界返回 null。同理建议对 `dv.getUint16(off + 28)` 等读取统一前置边界检查（现有 `off + 46 > n` 只保护了中央头本身）。

### 2.4 sw.js 浮动 Promise 与 CACHE_NAME 部署脚手架

1. `sw.js:62` 与 `sw.js:78` 的 `caches.open(CACHE_NAME).then((c) => c.put(req, copy))` 既未 await 也未 `.catch()`——cache 写失败会在 SW 里产生 unhandled rejection。低危，但一行 `.catch(() => {})` 可消除。
2. **部署脚手架**：资源走 cache-first（72-83 行），意味着**改了 `vendor/` 任何文件但忘记 bump `CACHE_NAME`（12 行）时，老用户会一直拿旧 vendor**（导航请求是网络优先不受影响，会出现「新版 index + 旧版库」的混搭）。已核对 `docs/RELEASE-CHECKLIST.md`：其中只有 package.json 版本 bump / tag / SHA256 留存等条目，**没有「改 vendor/ 必须同步 bump CACHE_NAME」一项**，建议补入（这是当前发布流程里唯一的静默坑）。

### 2.5 嗅探依赖前 64KB 内出现 `word/` / `xl/`

**位置**：`src/sniff.js:74`（head = 64KB）+ `88-93`（`ascii.includes('word/')` 等）

ZIP 系判断靠在**前 64KB** 里找目录名。若 docx/xlsx 的首个 zip 条目超过 64KB（媒体文件排在 document.xml 前的非 Word 系打包工具可产生），`word/` 不在窗口内 → 误判为普通 zip → 拒转。Word 自己生成的文件总是小元文件在前，故频率低。项目已有 `zipEntry`（xlsx.js，读中央目录）设施，可复用做兜底：窗口内找不到时查中央目录再判一次。

### 2.6 pdf.js 未配置 `cMapUrl`：非嵌入 CJK 字体 PDF 会整本走 OCR

**位置**：`src/pdf.js:129`（`getDocument({ data: buf, isEvalSupported: false })`）

未传 `cMapUrl` / `cMapPacked`。使用**非嵌入 CJK 字体**（依赖阅读器内置字体，国内导出工具常见）的 PDF，文本层提取会得到乱码或空串 → 每页命中「文本量 <10 字符」的 OCR 降级条件 → 整本逐页 OCR，耗时从秒级变成分钟级且质量更差。pdfjs-dist 自带 `cmaps/` 目录，打包进 `vendor/cmaps/` 并配置 `cMapUrl: './vendor/cmaps/', cMapPacked: true` 即可（代价约 1MB 离线资源 + SW 预缓存清单更新）。对以中文用户为主的产品，这条的**实际收益可能高于多数 P3**，只因涉及体积取舍暂列此级。

## 3. 可优化项（非 bug）

### 3.1 CI 缺「构建一致性」检查（复审 §2.6 已建议，本次确认仍未做）

`tests.yml` 只有 lint → test → audit → ocr，没有 build + diff。加一步即可防止「只改 src/ 忘构建、线上跑旧逻辑」：

```yaml
- name: Build consistency (src/ ↔ index.html)
  run: |
    npm run build
    git diff --exit-code index.html
```

本次实测构建幂等（§0.5），此步骤当前必绿，加上没有成本。

### 3.2 deploy-pages.yml 上传整仓（`path: .`）

Pages 产物含 `src/`、`tests/`、`docs/`、`tools/`、`package.json` 等非站点文件（`upload-pages-artifact` 会跟随 checkout 树；gitignored 文件不在 CI 检出中，无泄漏）。无害但多余、拖慢部署；可改为白名单上传站点所需文件（注意保留 `.nojekyll`、`vendor/`、`langs/`、`icons/`、`manifest.json`、`sw.js`、`index.html`）。

### 3.3 `copyText` fallback 不检查 `execCommand` 返回值

`src/ui.js:33`：`document.execCommand('copy')` 返回 boolean（false = 失败），当前忽略返回值，失败也会显示「✅ 已复制」。file:// 下该路径正是主路径，建议失败时显示「❌ 复制失败，请手动选择文本」。

### 3.4 拖放高亮闪烁

`src/app.js:35`：`dragleave` 注册在 window 上且冒泡——在 dropzone 内部子元素间移动时，离开子元素即触发（移除 `over` 类），紧接的 dragover 又加回，高亮闪烁。修法：dragenter/dragleave 计数器，或 dragleave 时检查 `e.relatedTarget` 是否仍在 dropzone 内。纯视觉问题。

### 3.5 TXT 路径的空行归一化会改变原文

`src/convert.js:39`：`\n{3,}` 强制压成 `\n\n`，会吃掉故意留白的文本（ASCII art、诗歌排版、代码段间多空行）。归一化口径问题而非错误，建议至少在 README「TXT 说明」处注明，或改为只 trim 首尾。
