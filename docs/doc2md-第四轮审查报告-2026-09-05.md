## 1. 新确认的 Bug（前三轮未覆盖）

### 1.1 文本解码三处缺陷：Big5 被按 GB18030 解码；charset 只查第一个 `<meta>`；纯文本 GBK 启发式漏判（P1/P1/P2）

**位置**：`src/sniff.js:20-71`（`decodeText`）

**根因与现象**：

**① Big5 命中分支后仍用 gb18030 解码（P1）**
```js
// src/sniff.js:57-59
if (val === 'gb2312' || val === 'gbk' || val === 'gb18030' || val === 'big5') {
  try { return new TextDecoder('gb18030').decode(buf); }
```
`big5` 与 GB 系是**不同编码**。浏览器 `TextDecoder` 原生支持 `'big5'` label，此处却统一按 gb18030 解。实测（file:// 浏览器挂钩 `decodeText`）：
- 输入：`<meta charset="big5">` + Big5 字节 `A7 41 A6 6E`（「你好」）
- 期望：`你好`；实际：``（gb18030 误读）

**② 只检查第一个 `<meta>` 标签，viewport 在前时漏检 charset（P1）**
```js
const metaIdx = headTxt.indexOf('<meta');
// 只取第一个 meta 切片后即解析 charset
```
老页面常见的 `<meta name="viewport">` 在前、`<meta charset="gb2312">` 在后的结构会漏检。实测：
- 输入：viewport 在前 + `charset=gb2312` + GBK「hello 你好」
- 期望：`hello 你好`；实际：`hello ���`（因头部 ASCII 占比高，30% 替换字符启发式也不触发）

**③ 无 meta 纯文本的 30% 替换字符阈值漏判（P2）**
```js
if (tot > 0 && bad / tot > 0.30) { /* 回退 gb18030 */ }
```
实测：`hello world 你好`（GBK，无 meta）→ 替换字符占比 20%（3/15）→ 不回退 → 输出 `hello world ���`。GB18030 是全覆盖编码，其解码结果几乎不会产生 U+FFFD，因此可用「UTF-8 出现任意 U+FFFD 且 GB18030 解码无 U+FFFD」替代固定阈值。

**修复方向**（不改动公开接口）：
1. 用循环 `indexOf('<meta')` 线性扫描**所有** meta，找到第一个带 charset 的声明（符合项目 t12 线性写法纪律）；
2. 按声明 label 映射解码：`gb2312|gbk|gb18030 → 'gb18030'`、`big5 → 'big5'`；
3. 启发式改为：UTF-8 容错解码出现 U+FFFD，且 `new TextDecoder('gb18030').decode(buf)` 不含 U+FFFD 时回退；否则保持 UTF-8。

**回归用例建议**（F 组扩展，浏览器环境）：
- Big5 meta 样例：断言 `decodeText` 输出含「你好」；
- viewport-meta 在前样例：断言 GB2312 中文正确；
- 无 meta 的短中文 GBK 文本：断言不出现 U+FFFD。

### 1.2 file:// 双击打开时 OCR 报原始 `Failed to fetch`，README 未提示（P2）

**位置**：`src/ocr.js`（`getOcrWorker` → `BLINE.tessWorkerUrl()` 的 fetch）+ `src/bline.js:33`

**现象**（本次 file:// 浏览器实测）：PNG OCR 转换 2ms 即失败，错误文案为 `转换失败：Failed to fetch`。根因是 Chrome 禁止 file:// 页面 fetch 本地文件，BLINE 的 `fetchTxt('./vendor/tesseract.worker.min.js')` 直接抛原始 TypeError。

**背景**：DEV-NOTES/design-decisions 已把该限制记为「预期内」，但 **README 使用方法只写「发布前双击 index.html 即可」，未注明 OCR 例外**；用户双击后拖入图片只会得到一句英文浏览器错误。PDF 文本层、DOCX、XLSX 在 file:// 下均已实测可用，仅 OCR 不可用。

**修复方向**：
1. `getOcrWorker` 开头检测 `location.protocol === 'file:'`，抛出可行动错误，如：「OCR 在 file:// 直开下不可用（浏览器限制），请用本地 HTTP 服务（如 `npx serve`）打开，其他格式不受影响」；
2. README「怎么用」与功能表加一行 file:// OCR 限制说明。

**回归用例建议**：README 口径核对 + 浏览器 file:// 下 OCR 用例断言错误文案可行动（新增 H 组纯源码断言也可覆盖：`ocr.js` 含 file: 检测分支）。

### 1.3 SW activate 删除整个 origin 下所有非本缓存，会误删同源其他 PWA 的缓存（P2）

**位置**：`sw.js:44-46`
```js
caches.keys()
  .then((keys) => Promise.all(keys.filter((k) => k !== CACHE_NAME).map((k) => caches.delete(k))))
```
Cache Storage 按 **origin** 共享。`sakuraqqq.github.io` 若还部署了其它 PWA（GitHub Pages 用户很常见的形态），doc2md 的 SW 激活时会清掉它们的缓存（数据不丢，但造成全量重下与可能的离线失效）。前三轮 2.4 只提了「浮动 Promise」与「CACHE_NAME bump」，未提越权清理。

**修复**：只清理本应用前缀的缓存：
```js
keys.filter((k) => k.startsWith('doc2md-') && k !== CACHE_NAME)
```
（与 `CACHE_NAME = 'doc2md-sw-v4'` 命名体系一致。）

### 1.4 测试侧：C3「image OCR <500ms」与 T-1 冷启动豁免口径矛盾（P2，CI 抖动风险）

**位置**：`tests/contract_v1.test.mjs:311`、CONTRACT.md T-1

CONTRACT.md T-1 拍板「lazy-init 冷启动不计入」；`ocr.js` 注释也写「首次 OCR 冷启动按 T-1 档位豁免」。但 `runConvertCase` 对**所有用例无条件**断言 `elapsedMs < 500`，且每个用例 `launchBrowser()` 新建浏览器 → image 用例每次都是冷启动（首次 OCR 需 fetch worker ≈111KB + wasm core ≈4MB + 语言包 ≈7.4MB + 初始化）。在共享的 GitHub runner 上 500ms 预算很容易击穿；即使不击穿，断言与拍板口径也不一致。

**修复方向**（二选一）：
1. image 用例做两段计时：先 `page.evaluate(() => window.__doc2md.convert(预热File))` 不计时，再计正式转换；
2. 为 image 用例加 per-case `thresholdMs` 覆盖（如 5000ms）并注释引用 T-1。

### 1.5 README「无浏览器时以 npm run test:direct 跑静态组」失实（P3）

**位置**：README.md L91

实测：`npm run test:direct` 只是直接执行 `tests/contract_v1.test.mjs`，D/E/F/G/I/J/K/L 静态快照组全部通过 `launchBrowser()` 跑在浏览器里；无浏览器时本机实测 47 测试中 25 失败。真正无浏览器依赖的只有 A/B/H/k5。README 应改为：「test:direct 同样需要浏览器（仅 A/B/H 静态组可不依赖浏览器）；或为测试加无浏览器 skip 门控后恢复该表述」。

### 1.6 `li` 内块级段落被拍平成一行（P3，保真度）

**位置**：`src/html2md.js:187-208`（`liToLines` 对非 UL/OL 子元素统一走 `fragFor` 平铺）

实测：`<ul><li><p>a</p><p>b</p></li></ul>` → `- a b`（两段并成一行）。list 内嵌 P 在 Word 导出的 HTML 中常见。建议：LI 内 P/DIV 等块级子节点作为独立段落处理（首段接 marker，后续段用续行缩进），或至少用两个 `<br>` 语义分隔。
