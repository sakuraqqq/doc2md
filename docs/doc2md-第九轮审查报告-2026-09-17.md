## 2. P1（建议下一版前修）

### 2.1 一个文件读取失败会让整批转换中断

**位置**：`src/app.js:15-26`（`handleFiles`）、`src/convert.js:117-118`（try 之外）

```js
// app.js
for (let i = 0; i < list.length; i++) {
  const file = list[i];
  const result = await convert(file);   // ← 无 try/catch
  renderResult(file, result);
}
setStatus('完成：共 ' + list.length + ' 个文件。');

// convert.js
const guard = guardError(file);
if (guard) return done({ error: guard });
const buf = new Uint8Array(await file.arrayBuffer());   // ← try 之外
const s = await sniff(buf);                             // ← try 之外
try { return await runConverter(...) } catch { ... }
```

**问题**：

- 多文件选择/拖入时，只要某一个文件在 `arrayBuffer()` 读取阶段失败（文件被移走、权限变化、极端 IO 等），`convert()` 会直接 reject；
- `handleFiles` 的循环没有逐文件捕获，剩余文件全部不再转换；
- `drop` / `change` 调用处也没有 `.catch`，会变成 unhandled rejection，状态栏可能永远停在“正在处理 N 个文件…”；
- 只有 `runConverter` 内部的异常被转成友好错误，读取/嗅探阶段不在其中。

**建议**：

- `convert()` 把 `arrayBuffer/sniff` 纳入 try，统一转成 `{ error }` 返回；
- `handleFiles` 对每个文件单独 try/catch，失败时渲染该文件的错误卡片并 `continue`；
- 末尾状态改为“完成：X 成功 / Y 失败”，并给两个事件入口补 `.catch`。

### 2.2 `deploy-smoke.mjs` 站点白名单守卫可被绕过

**位置**：`tools/deploy-smoke.mjs:20-48`

该脚本的目标是防“新增必需顶层文件被静默漏发”，目前有两种已实测的假绿：

#### 假绿 A：只匹配双引号属性

```js
for (const m of html.matchAll(/<(?:script|img)\b[^>]*\bsrc="([^"]+)"/g)) refs.add(m[1]);
for (const m of html.matchAll(/<link\b[^>]*\bhref="([^"]+)"/g)) refs.add(m[1]);
```

`src='vendor/missing.js'` 这类单引号写法不会进入 `refs`。

**实测**：临时 `_site` 的 `index.html` 引用不存在的 `vendor/missing.js`（单引号写法），脚本输出

```text
[deploy-smoke] PASS——同源引用 0 个全部可解析，必需顶层文件/目录齐备
EXIT=0
```

#### 假绿 B：`../` 引用按文件系统路径解析，而不是按站点 URL 解析

```js
const p = path.join(site, clean.replace(/^\.\//, ''));
if (!fs.existsSync(p)) missing.push(...)
```

浏览器里 `<script src="../outside.js">` 会解析到站点根下的 `/outside.js`；但脚本用
`path.join(site, '../outside.js')` 去找，会命中仓库父目录里的文件。

**实测**：`_site` 内没有 `outside.js`，父目录有；脚本输出 PASS。

#### 其它缺口

- 不解析 `manifest.json` 的 `icons[].src` / `start_url` / `scope`，图标缺失也能 PASS；
- 只检查“必需的有”，不检查 `_site` 里是否混进 `tests/`、`docs/`、`.私档/`、`.tmp/` 等禁止公开路径；
- 不匹配 `srcset` / 内联 CSS `url(...)` 引用；
- 只在 tag/手动部署流程里运行，PR/主干 CI 不会在组装临时 `_site` 后跑它。

**建议**：

- 引用提取支持单/双引号与 `srcset`；
- 以站点根为 URL 基准解析引用，拒绝任何 `..` 逃逸（解析后必须仍在 `site` 内）；
- 校验 `manifest.json` 的资源字段，并对 `_site` 做“禁止路径不得出现”的反向扫描；
- 在 `tests.yml` 增加“组装临时 `_site` + deploy-smoke”步骤。

### 2.3 `audit-delivery.mjs` 的存在性守卫与离线口径有洞

**位置**：`tools/audit-delivery.mjs:51-59`、`93-107`、`109-119`、`160-166`

#### 洞 1：交付面清单缺包不报错

```js
function deliveryVersions() {
  const out = new Map();
  for (const name of DELIVERY_FACE) {
    const version = lock.packages?.[`node_modules/${name}`]?.version;
    if (version) out.set(name, version);   // ← 缺包静默跳过
  }
  return out;
}
...
if (versions.size === 0) { /* 只有全缺才红 */ }
```

六个交付包里少一个（改名、换锁结构、被嵌套安装等）时 `versions.size` 仍 > 0，门禁会静默少审。

#### 洞 2：`mammoth` 内联在 vendor 但不在交付面清单

脚本注释明确写了 `mammoth@1.12.2` 已内联在 `vendor/`，但未在 `package.json` 声明，因此被登记为“人工跟踪项”。这意味着：

- mammoth 的 CVE/许可/版本漂移**完全不进自动门禁**；
- 换 vendor 文件却忘记人工复核时，没有任何守卫会红。

#### 洞 3：离线 `npm audit --json` 路径会把传递链归到交付包头上

```js
function viaItems(name, v) {
  const via = Array.isArray(v.via) ? v.via.filter((x) => typeof x === 'object') : [];
  if (via.length === 0) {
    return [{ pkg: name, id: '(transitive)', severity: low(v.severity), ... }];
  }
  ...
}
```

`npm audit --json` 在传递依赖告警时常用字符串 `via`（如 `via: ['tar']`）。此时函数会生成一条
`{ pkg: 'pdfjs-dist', id: '(transitive)', severity: 'critical' }`，随后被判为交付面未豁免 critical。

**逻辑复算实测**：

```js
viaItems('pdfjs-dist', { via: ['tar'], severity: 'critical' })
// → [ { pkg: 'pdfjs-dist', id: '(transitive)', severity: 'critical' } ]
```

这与脚本注释声明的“dev/optional 传递链不进交付面、不阻断”口径相反（当前 `canvas → node-pre-gyp → tar` 正是 won’t-fix 链）。

#### 其它

- `fetchAdvisories()` 没有超时；registry 卡住时 CI 会等到 job timeout。
- 没有校验 `package-lock.json` 里的版本与 `vendor/` 实际内联文件 / `docs/licenses.md` 登记版本一致，版本漂移无法自动发现。

**建议**：

- 要求 `DELIVERY_FACE` 每一项都必须解析到，缺失要显式列例外；
- 给 `mammoth` 建立机器可读的 vendor 清单（名称/版本/来源/许可/SHA），纳入审计；
- 离线模式只对 `via` 对象条目做归因，纯字符串传递链不做父包归因；
- fetch 加 `AbortSignal.timeout(...)`；
- 增加“lock 版本 ↔ vendor 资产 ↔ licenses.md”交叉校验。

## 3. P2（值得修，但不阻塞当前线上）

### 3.1 docx 图片 alt 会把 `descr` 当文件名去“扩展名”

**位置**：`src/docx.js:33-38`

```js
const n = String(entry.descr || '').trim() || String(entry.name || '').trim();
return n.replace(/\.[A-Za-z0-9]{1,8}$/, '');
```

`descr` 是 Word 的“可选文字/题注”，不是文件名。该正则会把任何以 `.字母/数字` 结尾的题注截断。实测：

```text
"Figure 3.1"     => "Figure 3"
"版本 1.2"       => "版本 1"
"Screenshot 2.0" => "Screenshot 2"
"v1.2"           => "v1"
```

现有 V4 夹具 `ALT-FROM-DESCR-2026` 不带点号，因此没有暴露。

**建议**：去扩展名只对 `name` 执行，且只匹配已知图片扩展名（png/jpg/jpeg/gif/bmp/webp/tif/tiff/emf/wmf/svg）；`descr` 只 trim、不改写。

### 3.2 docx 图片 alt 的“按回调顺序对号”有漂移风险

**位置**：`src/docx.js:128-134`（收集 `pic:cNvPr`）、`src/docx.js:268-283`（`state.idx++` 对应）

`docxImageNames()` 按 `pic:cNvPr` 文档序收集 name/descr；`docxImageElement()` 假设 mammoth 的 `convertImage` 回调**每个 cNvPr 恰好一次且顺序一致**。在以下形态可能漂移：

- DrawingML + VML fallback（同一视觉图片触发多次回调）；
- 文本框/形状内的图片；
- mammoth 跳过或额外处理某些图片。

一旦数量/顺序错位，后面的 alt 会整体错位，且目前没有数量一致性检查或 warning。

**建议**：至少比较 `state.idx` 与 `imgNames.length`，不等时 warning；更稳妥是按关系 ID/媒体路径关联 alt，而不是依赖回调顺序。

### 3.3 PDF `BT` 不重置 `flip`，跨 BT 块继承上一块朝向

**位置**：`src/pdf.js:132-148`、`150-153`

代码注释明确写着：`BT` 只复位 `cx/cy/lx/sx/sy`，`leading` 与 `flip` 不重置。问题在于 PDF 规范规定 `BT` 会把文本矩阵/行矩阵重置为单位阵；`flip` 是从 Tm 的 d 符号派生的，不是独立文本状态参数。

若某个 `BT` 块设置了 flipped Tm，后续某个 `BT` 块没有重新设置 Tm（使用默认单位阵），`st.flip` 会沿用上一块，`screenY()` 排序与 `T*` 推进方向都会受影响。

**建议**：补一个“多 BT、仅首块有 Tm”的合成样例确认实际行为；若确认，`BT` 时重置 `flip=false`，或改为从页面级 CTM/变换推导朝向。

> 说明：该行为在现有注释中被标为“语义未动”，因此本条定位为“待夹具确认的边界”，不是直接判定当前必然错。

### 3.4 导出时单张图片读取失败会静默丢图

**位置**：`src/ui.js:61-65`（zip）、`src/ui.js:110-121`（单文件内嵌）

```js
// zip
try { files[a.name] = new Uint8Array(await a.blob.arrayBuffer()); }
catch { /* 单图读取失败跳过（其他图照常打包） */ }

// embed
try { bytes = new Uint8Array(await a.blob.arrayBuffer()); }
catch { /* 单图读取失败跳过（其他图照常内嵌） */ }
```

后果：

- zip 里少图，但 `.md` 仍引用 `assets/...`；
- 单文件内嵌模式仍残留 `assets/` 相对引用，违背“自包含”承诺；
- 用户看到的是“下载成功”，没有任何缺图提示。

**建议**：收集失败资产，在状态栏/结果 warnings 中明确“N 张图片读取失败，未写入导出件”，并决定中止导出或显著提示。

## 4. P3（优化项）

### 4.1 CI 使用 Node 20，与发布/验收运行时 Node 24 不一致

**位置**：`.github/workflows/tests.yml:29`

`node-version: 20`，但 v0.1.4–v0.1.9 的发布记录均为“Windows / Node 24.18.1 + 系统 Edge 回退”，且 `package.json` 没有 `engines` 声明。当前代码没有明显用到 22+ API，因此不是故障，但 CI 与真实运行时不统一，未来可能出现“CI 绿、用户机红”或反向问题。

**建议**：`package.json` 增加 `engines`；CI 对齐 Node 24，或做 20/24 双版本矩阵。

### 4.2 `extForContentType` 对 SVG/EMF/WMF 产生非标准扩展名

**位置**：`src/docx.js:21-27`

`image/svg+xml` → `.svg+xml`，`image/x-emf` → `.x-emf`，`image/x-wmf` → `.x-wmf`。功能可用，但资产名不标准。

**建议**：增加映射：`svg+xml → svg`、`x-emf → emf`、`x-wmf → wmf`（保留现有 jpeg/tiff 归一）。

### 4.3 GIF 尾部填充会被误判（与 backlog 相邻，不算重复）

**位置**：`src/sniff.js:216-220`

`isGif()` 要求文件最后一个字节必须是 `0x3B`（trailer）。实测把 `tests/data/sample.gif` 追加 1 个字节：

```text
原始： { type: 'image', detail: 'gif' }
追加： { type: 'unknown', detail: 'binary' }
```

合法 GIF 带尾部填充/附加元数据时会被误杀。

这不是重复 backlog 中的“GIF trailer 完整性校验（防文本误判正例）”；**在实现 backlog 那条时请避开反向坑**：按 GIF block 结构走到 trailer，不要只看末字节。

### 4.4 tag 推送本身没有测试门禁

**位置**：`.github/workflows/tests.yml`（`on: push: branches: [main]` + PR）、`.github/workflows/deploy-pages.yml`（tag push 部署）

「线上 == 发布物」已由 H15 守卫，但 **tag 推送不会触发 tests.yml**，deploy-pages 只跑 `deploy-smoke` 静态资源核对。若 tag 指向未经 main CI 的提交，仍可能直接部署。

**建议**：tests.yml 增加 `push: tags: ['v*']`（或抽成 reusable workflow，让 deploy-pages 先依赖它）；至少保证发布 tag 必须经过与 main 同款门禁。
