# doc2md v0.1.8（2026-09-15）

> 本版是**修复批**：修掉 v0.1.7 线上存在的三类**静默错**（编码判定误判）。完整发布记录见 `docs/RELEASE.md` 的「## v0.1.8」节。

## 修什么

**问题**：当文件里有**少量坏字节**、且非 ASCII 字符基数很小时，编码判定门会误判为 GBK，把**整篇**文本用 gb18030 重解一遍 —— 结果**不是报错**，而是输出一串**看起来像中文、其实是乱码**的字：

| 输入 | v0.1.7 输出（错） | v0.1.8 输出（对） |
|---|---|---|
| 短 UTF-8 中文 + 2 个坏字节 | `浣犲ソ涓栫晫浣犲ソ涓栫晫…` | `你好世界…`（保持原样 + 替换字符标记） |
| 纯 ASCII + 2×`0xB0` | 凭空出现汉字 | 原样保留 |
| 纯 ASCII + 2×`0x80` | 凭空出现 `€` | 原样保留 |

用户完全看不出来 —— 既没有报错，也没有任何提示。

**修复**：编码判定的门槛由「**≥2** 个替换字符」收紧为「**≥3** 个替换字符且占比达标」（`src/sniff.js` 两个常量）。

**为什么是 3 而不是更高**：实测 17 组样例后发现，门槛提到 **5** 会**误伤极短的真 GBK 文件**（例如 16 字节的 `hello world 你好` 会变成 `hello world ���`）—— 这是本版**刻意保住**的行为。

**已知边界（如实登记）**：**2 字节的单汉字 GBK 文件**不再自动回退（它与「2 处坏字节」的计数签名相同、无法区分）。这是为了保住上面那条更常见的场景而做的取舍，已锁进契约（组 S **S4-14**）。

## 兼容性 / 影响面

- **只改编码判定阈值**，不改任何格式解析逻辑：PDF / DOCX / XLSX / OCR 行为不变。
- 契约 **255 tests / 253 pass / 0 fail / 2 skip**（skip = 不入库的第三方样例）· lint **0** · metrics 超限 **0** · PWA **48/48** · 离线 OCR **PASS(93%)**。
- 产物 `index.html`：**120,987 B**（与上一构建**同长度** —— 页脚版本串等长），核对请一律以 **SHA256** 为准：
  `14773E5FFDE3072A33FCD127C1DDA6E8CF739CB8366F4D17BDDED0A5EBF3F178`
- **独立验收（Linux 侧，真 chromium）六项全绿**，含**双向负对照**：切回旧阈值 → 三条缺陷断言**必红**；切到候选阈值 5 → 短 GBK 断言**必红**（证明新门槛确实在守）。

## 零外发 / 离线（不变）

全部转换在**你自己的浏览器里**完成，无任何上传或外域请求；单目录离线、断网可用、可装到手机主屏。
